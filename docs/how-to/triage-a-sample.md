# Triage a sample

Triage produces a stable snapshot of a file: digest, format, architecture, entry point, entropy,
segments, imports, strings, and constants. It is intended for reproducibility and quick
classification, not for full function recovery.

The report is captured from the original bytes when the file is opened. It does not change when
you rename functions or add comments, and it is not regenerated by re-analysis. Reopen the file to
produce a fresh report.

## In the GUI

1. Open the binary (**File → Open Binary…**) or raw image (**File → Open Raw Image…**).
2. Choose **Windows → Triage**.
3. Read the header for the SHA-256, format, architecture, entry point, entropy, segment count, and
   import count.
4. Click a finding to highlight its bytes in **Hex View**.
5. Export with **Export JSON…** or **Export Markdown…**.

The export is written atomically: sleuthre writes a temporary file and replaces the destination
only after the full report has been flushed.

## From the CLI

JSON is the default:

```sh
cargo run -p re-cli -- triage path/to/binary > triage.json
```

Markdown is one flag away:

```sh
cargo run -p re-cli -- triage path/to/binary --format markdown > triage.md
```

For a raw image, supply the same mapping flags as the `raw` subcommand:

```sh
cargo run -p re-cli -- triage firmware.bin --arch arm64 \
  --region code:0:0x4000:0x8000 \
  --region data:0x4000:0x2000:0x200000 \
  --format markdown
```

The command writes the report to stdout. Progress from the loader is not written to stdout, so
redirecting the output produces a clean JSON or Markdown file.

## From MCP

`get_triage_report` returns the report for the currently open sample:

```json
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_triage_report","arguments":{"format":"markdown"}}}
```

The tool accepts only the optional `format` parameter (`json` by default, or `markdown`). Reports
larger than 8 MiB are rejected; export large reports with `re-cli triage` instead.

## Reading the report

| Field | Meaning |
|---|---|
| `schema_version` | Report layout version; current version is 1 |
| `sha256` | SHA-256 of the complete input bytes, including bytes outside the mapped regions |
| `format` | `Elf`, `Pe`, `MachO`, or `Raw` |
| `architecture` | Display name such as `x86_64`, `ARM64`, or `MIPS` |
| `byte_order` | Present for raw mappings; omitted for containers that declare it themselves |
| `entry_point` | Loaded entry address |
| `entropy` | Shannon entropy of the whole file in bits per byte, rounded to six decimals |
| `segments` | Mapped ranges with permissions and, for raw images, file offsets |
| `imports` | Imported names, libraries, and resolved addresses when available |
| `findings` | Extracted ASCII/UTF-16 strings and recognized constants, sorted by address |

Findings are evidence, not verdicts. A high entropy value suggests compressed or encrypted content;
a low value suggests padding or plain data. Neither is conclusive on its own.

## Comparing reports

Because the report contains a whole-file SHA-256, two reports describe the same input only when
their digests match. Compare digests first, then compare segment layouts and finding sets. The
[project file](../reference/project-format.md) retains the report alongside the analysis, so a
saved `.slre` can be used to revisit what was known at load time.
